# pyrio 1.0: foundation plan

This document replaces the earlier readiness audit. It does not try to preserve the
existing surface. It describes the library pyrio should be at 1.0 and what has to change
to get there. Backward compatibility with pre-1.0 pyrio is **not** a constraint. Every
design question gets one answer: whatever makes the best long-term foundation.

Already landed and not repeated here: the six public-surface bug fixes (`221b03e`) and
the Rio 2.3.0 result tables, with the deterministic parity test and the legacy 5/6 label
correction (`396deed`); and the field-parity test fix (it had scanned zero files since
the move to `src/`) with the per-position readers it then caught.

---

## 0. The archetype: python-chess

> **pyrio is python-chess for Mario Superstar Baseball.**

[python-chess](https://python-chess.readthedocs.io/) is the best precedent for what
pyrio is: a pure-Python, fully typed, dependency-free library for one game. It covers
the game's rules and data, reading and writing its game-record format, talking to an
engine, and rendering. Each part of pyrio has a counterpart there:

| python-chess | pyrio |
|---|---|
| `chess.PieceType`, `chess.Square`, `chess.Termination` — the game's vocabulary as typed constants | `Character`, `Stadium`, `AtBatResult`, … as enums (section 2) |
| `chess.pgn.read_game(handle) -> Game` — parse a game record once into objects | `pyrio.read_game(path) -> Game` from a stat file (section 3) |
| `game.headers`, `game.mainline_moves()`, `board.outcome() -> Outcome` | `game.stadium`, `game.events`, `game.result -> GameResult` |
| `chess.Board` — state at a point in the game | `Event.state` — count, outs, runners and score at a pitch |
| `chess.engine` — an engine as a context-managed client, sync and async | `pyrio.web.RioClient` (section 4) |
| `chess.svg.board(...) -> str` — rendering with no plotting dependency | `pyrio.svg.stadium(...) -> str`, plus an optional matplotlib adapter (section 6) |
| `chess.polyglot`, `chess.syzygy` — readers for the game's data files | `pyrio.geometry` — collision meshes, walls and hazards (section 5) |
| zero runtime dependencies | zero runtime dependencies too; httpx, pandas and matplotlib as extras (section 7a) |

**Settling a design question:** ask what python-chess would do. It names things after
the domain. Game records parse straight into objects. Constants are typed and complete.
Rendering, engines and file formats each get their own submodule. Nothing does I/O
unless you asked it to. There's one obvious way to do each thing.

For the web client, the archetype is **httpx**: a context-managed client, explicit
timeouts, typed methods with real signatures, and errors raised from one hierarchy.

## 1. Principles

These are standard practices for a typed library that parses data and wraps an API.
Each later section applies them.

1. **Parse, don't validate.** Decode raw input (stat-file JSON, API responses) once, at
   the edge, into typed immutable objects. Code past that point never sees a raw dict, a
   raw id, a raw label or a version number.
2. **Enums for coded values.** Every id↔name table becomes an `enum.Enum`, so users get
   autocomplete, typo-checking, `match` exhaustiveness and iteration.
3. **Data is attributes, computation is methods.** Write `game.stadium`, not
   `game.stadium()`. Methods are for things that take arguments or do real work.
4. **Domain words, snake_case, no sentinels.** `Side.HOME`, not `teamNum=1`.
   `team.batting`, not `rosterNum=-1`.
5. **One way to do each thing.** No parallel `*_from_event` variants, no
   `raw=True` / DataFrame / dict triple paths, no deprecated aliases.
6. **An explicit public API.** Each module has an `__all__`, and implementation modules
   are underscore-prefixed. `__init__.py` re-exports the core.
7. **No side effects you didn't ask for.** No I/O at import, no `print`, no reading the
   environment or working directory implicitly. Use `logging.getLogger(__name__)` for
   diagnostics and `warnings` for real warnings.
8. **Errors are specific and catchable.** One `RioError` base, specific subclasses that
   also inherit the matching stdlib type, and never a sentinel return value.
9. **A minimal core.** The core needs nothing beyond the standard library. httpx,
   pandas and matplotlib are opt-in extras; scipy and numpy are gone.
10. **Machine-checked.** pyright strict, ruff, pytest with coverage, and CI on every
    supported Python version.

## 2. Coded values → enums

### Target

```python
class Stadium(CodeEnum):
    MARIO_STADIUM = 0, "Mario Stadium"
    BOWSER_CASTLE = 1, "Bowser Castle", "Bowser's Castle"   # trailing strings are aliases
    ...

Stadium.BOWSER_CASTLE          # static, autocompletes, pyright-checked
Stadium(1)                     # by id
Stadium("bowser's castle")     # by label or alias, case-insensitive (via _missing_)
Stadium.BOWSER_CASTLE.label    # 'Bowser Castle'
Stadium.BOWSER_CASTLE.id       # 1
list(Stadium), len(Stadium)    # iteration for free
match event.result:
    case AtBatResult.SINGLE | AtBatResult.DOUBLE: ...
```

`CodeEnum(Enum)` is about 30 lines. `__new__` takes `(id, label, *aliases)` and sets
`_value_ = id`. A `_missing_` resolves labels, aliases and digit strings through a
case-insensitive index built once per class. It also defines `.id`, `.label`,
`__str__ -> label`, `__int__ -> id`, and ordering by id within a type, so `sorted()`
works. RioVisualizer's `stat_summary` currently raises `TypeError` on
`sorted(batters)` because value objects can't be compared.

Enums also carry the domain groupings callers currently hard-code as magic numbers:
`AtBatResult.is_hit`, `.is_out`, `.is_walk`, `.bases` (1–4 or 0), `ContactType.is_sour`,
and so on. League Tools' wOBA script spells "outs" as `{1, 4, 5, 6, 14, 15, 16}`. It's a plain `Enum`, **not** `IntEnum`, so a
member never equals a raw `int` or `str`. That keeps the original "value-to-value only"
decision, and pyright flags `stadium == "Mario Stadium"` as an always-false comparison
instead of letting it pass silently.

Members are interned singletons, so compare them with `is`. Lookups are dict hits.
Today `from_raw` costs about 8 µs (22 µs for characters), and construction does no
validation at all.

### Hand-written, machine-checked

`_codes.py` and `_characters.py` are written and maintained by hand: the enum members,
their comments and their behaviour live together in readable files. `tests/test_canonical_parity.py`
already parses `MSB_StatTracker.h` at a pinned ref, compares, and tracks deliberate
divergences. It's pointed at the enums instead of `Tables`. There's no code generator.

An earlier draft proposed generating the enums from the header. That was rejected:

- **The data is small and slow-moving.** There are about 260 members across 19 tables.
  Rio 2.3.0 was the largest table change ever, and it was 9 rows. A generator would be
  more code than the data it maintains.
- **Generated files can't carry behaviour cleanly.** `AtBatResult.is_hit`,
  `Character.attributes`, aliases, and comments like the 5/6 note belong in the class
  body. With generation they need "DO NOT EDIT" regions, mixins, or override tables
  inside the tool. That's indirection whose only job is avoiding typing a line now and
  then.
- **The hand-made parts are decisions, not data.** Member names (`"1B"` → `FIRST_BASE`,
  `"Walk (HBP)"` → `HIT_BY_PITCH`), aliases (legacy stadium names, `"Error - Input"`),
  value aliases (canonical `cFielderBobbles` / `cStealType` both map `0` and `0xFF` to
  `"None"`, which resolve to one `NONE` member), and pending-upstream divergences
  (id 12, ProjectRio#170) are judgement calls. They're reviewed best where they live.
- **Diffs stay honest.** A reviewer sees the line that changed, not a regenerated file.

The test keeps the one thing a generator offered, low-effort updates. When upstream
adds or renames an id, the failure message prints the exact line to paste:

```
Character vs canonical cCharIdToCharName (ProjectRio @ origin/2.4.0_release, 1a2b3c4d5e)
  missing id 54 'Captain Toad' -- add:    CAPTAIN_TOAD = 54, "Captain Toad"
```

The test also checks the reverse direction: every enum member must exist upstream or
be listed in `PENDING_UPSTREAM`.

**It must run in CI, not just locally.** Today the test *skips* unless a ProjectRio
checkout sits next to pyrio, which means it only ever runs on one machine. The CI job
does a sparse checkout of the public `ProjectRio/ProjectRio` repo at the pinned ref (the
header and `.cpp` only), so drift fails the build for everyone. Bumping the pinned ref
is a deliberate, reviewed one-line change, made when pyrio adopts a Rio release.

### Specific types

- **`InputDirection(Flag)`** with `LEFT=1`, `RIGHT=2`, `DOWN=4`, `UP=8`. The table
  is a bitmask, so `Flag` fits exactly: `InputDirection.LEFT | InputDirection.UP`, and
  `InputDirection.UP in d`. It also removes `HitInputs`' four `input_*` bools.
- **`Character`** members carry `.family -> CharacterFamily`,
  `.attributes -> CharacterAttributes`, and `.is_captain`. See section 2b for families
  and section 2c for nicknames and other human input.
- **Categoricals** in `character_data.py` (`CharacterClass`, hit trajectories, …) become enums
  too, and `CharacterAttributes` fields use them.
- **`Position`** has no `None` member. An absent position is `Position | None`.
- **`Side(Enum)`** `AWAY`, `HOME`, which replaces `team_num` everywhere (section 3).
- **`Hand`** absorbs `HAND_BOOL`. One concept, one type.
- `live_ball` collision kinds become an internal `IntEnum` (decomp ids, not canonical).

### Deleted

`Tables`, `RioValue`, `BaseCharacter`, `from_raw`, `lookup()`, `list_dicts()`,
`simplified_name_groups()`, `userInputToCharacter` (now `Character.parse`, section 2c),
`is_captain()` (now `Character.parse("bj").is_captain`), `_single_lookup`, `_resource_path`, and `HAND_BOOL`. Bulk
translation of DataFrame columns moves to `pyrio.pandas` (section 7). It uses
`{m.id: m.label for m in Cls}` maps built once, which also fixes today's O(rows × table)
cost.

## 2b. Characters and character families

### The concept

MSSB has 54 playable characters (canonical ids 0–53) but only **32 families**. Nine
families come in variants: Toad ×5, Shy Guy ×5, Magikoopa ×4, Dry Bones ×4, Pianta ×3,
Noki ×3, Bro ×3 (Hammer/Fire/Boomerang), Koopa ×2, Paratroopa ×2. The other 23 families
have exactly one member. Some questions are about a variant ("how fast is Toad(B)?") and
some are about a family. Team names, for example, are defined by family: a roster
signature needs *a* Toad, not Toad(R).

### What's there today, and what's wrong with it

- **`Tables.SIMPLIFIED_NAME`** is a 54-row variant → family-name table, and 23 of its
  rows are identity (`'Mario': 'Mario'`).
- **`BaseCharacter`** is a separate value class keyed by that string. It reimplements
  `RioValue`'s dunders and is reached through `Character.base`, `name_no_variant` and
  `simplified_name_groups()`.
- **`BaseCharacter.attributes` returns wrong data.** It returns the *full* attribute
  record of a "representative variant", but **22 of the 45 attribute fields differ
  within a family** (measured): `speed`, `charge_hit_power`, `slap_hit_power`,
  `fast_ball_speed`, `curve`, `throwing_power`, the non-captain star moves, the bat
  ranges and more. So `BaseCharacter("Toad").attributes.speed` silently answers with
  Toad(R)'s speed. Only `char_class`, `is_captain`, the fielding abilities, `weight` and
  a few others (23 fields) are actually shared.
- **Callers fake families with strings.** RioBot's alias `"toad": 13` maps to Toad(R),
  so `!stats toad` silently shows Red Toad only. Its "grouped character" branch can't be
  reached, because nothing maps to a list. PRSH normalises captains through
  `Lookup.lookup("simplified_name", ...)`.

### Target

```python
class CharacterFamily(Enum):           # 32 members, hand-written like _codes.py
    MARIO = "Mario"
    TOAD = "Toad"
    BRO = "Bro"
    ...

Character.TOAD_B.family                # CharacterFamily.TOAD
CharacterFamily.TOAD.variants          # (Character.TOAD_R, TOAD_B, TOAD_Y, TOAD_G, TOAD_P), in id order
CharacterFamily.MARIO.variants         # (Character.MARIO,)
CharacterFamily.TOAD.has_variants      # True
CharacterFamily("Shy Guy")             # by family label, case-insensitive
CharacterFamily.parse("bones")         # human input, nicknames included (section 2c)
CharacterFamily.TOAD.char_class        # shared facts only: char_class, is_captain, abilities
```

Design decisions:

1. **A plain `Enum`, not a `CodeEnum`.** Rio assigns families no id, so we don't invent
   one. The value is the label. Members are defined in order of their first variant's
   char id, and that definition order is the sort order.
2. **No table.** Family membership comes from the canonical label form `Name(Variant)`.
   The family is the part before the parenthesis, and every current label fits. The
   54-row `SIMPLIFIED_NAME` table is deleted. A test pins the membership of all 9
   multi-variant families and asserts every `Character` lands in exactly one family. If
   Rio ever renamed `"Toad(R)"` to `"Red Toad"`, the test would fail loudly rather than
   misgroup.
3. **A family exposes only what's genuinely shared.** It has `char_class`, `is_captain`
   and `abilities` (the fielding-ability set), and **no `.attributes`**. Per-variant
   numbers are reached through a variant, so the "representative variant" bug can't
   exist. A test asserts that every property a family exposes really is invariant
   across its variants. If a data change ever breaks that, the test fails.
4. **Distinct types, never equal.** `Character.MARIO` and `CharacterFamily.MARIO` are
   different things, and `Character.MARIO.family is CharacterFamily.MARIO` is how you
   relate them. That matches the enum rule that values never compare equal across types.
5. **Strict constructor, lenient `parse`.** `CharacterFamily(str)` accepts only a family
   label. Human input goes through `CharacterFamily.parse` (section 2c). Neither accepts
   a `Character` member: `.family` is the one spelling for that conversion.
6. **No `Character.variant` attribute yet.** The suffixes aren't one concept: `(R)` is a
   colour, but `Bro(H)` is Hammer. Add it when a caller needs it, as its own small type.

### Aggregating by family

`BattingLine` and `PitchingLine` support `+`, with an empty line as the identity. That
makes family totals one line, and it's also how `Team.batting` sums the roster:

```python
toad = sum((stats[c].batting for c in CharacterFamily.TOAD.variants), BattingLine())
toad.ops
```

That's the RioBot `!stats toad` command done properly.

### Who changes

- `team_name_algo`: `Signature.members` becomes `frozenset[CharacterFamily]` and
  `roster_bases = {c.base ...}` becomes `{c.family ...}`. The logic is unchanged.
- `CAPTAIN_TEAMS` stays keyed by captain `Character`. Captains have no variants, so PRSH
  looks up `CAPTAIN_TEAMS[Character(captain)]` directly, with no family normalisation.
- Deleted: `BaseCharacter`, `Character.base`, `Character.name_no_variant`,
  `Tables.SIMPLIFIED_NAME`, `simplified_name_groups()`, `_SIMPLIFIED_NAMES` and
  `_BASE_REPRESENTATIVE_ID`.

## 2c. Human input: nicknames, shorthand, typos

### What's there today

- **`CharNames.csv`** holds 264 hand-curated aliases: codes (`bj`, `rsg`), spellings
  (`donkeykong`), colour forms (`r!toad`, `redtoad`, `toad(r)`) and community
  nicknames (`greg`, `teardrop`, `cornpop`, `johndeere`). **The char id is the row
  number**, so inserting a line silently reassigns every character below it.
- **`userInputToCharacter`** lowercases and strips spaces, nothing else.
  `"Bowser Jr."`, `"bowser-jr"`, `"Petey Piranha"`, `"Diddy Kong"` and `"Toad (Red)"`
  all fail. It returns a name string, and a miss gives no suggestion.
- **There were three diverged copies.** RioBot keeps its own 272-entry alias table, with
  122 nicknames pyrio lacks (`dingus`, `bowserjunior`, `bonesgrey`, …). It **disagrees
  with pyrio on 7 keys**: `koopa` means Koopa(R) to the bot and Koopa(G) to pyrio, and
  `pianta`, `noki`, `bones` and `para` each pick a different variant. `pt` is
  Paratroopa(G) to the bot and Toad(P) to pyrio, and `bb` is Pianta(B) versus
  Boomerang Bro. The Event Search app ships a third copy of the CSV with an even weaker
  resolver (lowercase only).

So "which Koopa is `koopa`" depended on which tool you asked. Shared, curated human-input
data is exactly what a library is for.

**Decided (2026-11-21).** A bare family name means a chosen default variant, and the
contested shorthands are settled. `CharNames.csv` already carries these, and
`tests/test_lookup_values.py::test_family_name_defaults` pins them:

| Typed | Means | | Typed | Means |
|---|---|---|---|---|
| `koopa` | Koopa(R) | | `toad` | Toad(R) |
| `pianta` | Pianta(R) | | `shyguy` | Shy Guy(R) |
| `noki` | Noki(G) | | `magikoopa`, `mag` | Magikoopa(B) |
| `bones`, `drybones` | Dry Bones(G) | | `bro` | Bro(H) |
| `para`, `paratroopa` | Paratroopa(G) | | `pt` | Toad(P) |
| | | | `bb` | Bro(B) |

When RioBot moves to pyrio, its `pt` (Paratroopa(G)) and `bb` (Pianta(B)) change
meaning. Its other five contested keys already match.

### Target: two doors

```python
Character(29)                    # strict: id, canonical label (case-insensitive), legacy label
Character("Toad(B)")

Character.parse("Bowser Jr.")    # lenient: human input
Character.parse("teardrop")      # Character.TOAD_B
Character.parse("toad blue")     # Character.TOAD_B
Character.parse("koopa")         # Character.KOOPA_R -- the family's default variant
CharacterFamily.parse("koopa")   # CharacterFamily.KOOPA -- the family itself
Character.parse("peech")         # UnknownNameError: 'peech' -- did you mean Peach?
```

1. **Strict and lenient are separate methods.** `Character(x)` is for machine input
   (stat files, API rows) and only accepts exact ids and labels. That way a stray `"b"`
   in data is an error, not Boo. `Character.parse(text)` and
   `CharacterFamily.parse(text)` are for people. They're the only way nicknames get
   resolved.
2. **Normalisation is one function.** Casefold, apply NFKC, then drop everything that
   isn't a letter or digit. `"Bowser Jr."`, `"bowser-jr"` and `"BOWSER JR"` all become
   `bowserjr`, and `"Toad (Red)"`, `"toad(r)"` and `"r!toad"` all become forms the
   resolver knows.
3. **Variant forms come from a rule, not from listing.** Each multi-variant family
   declares its variant words: `R → red`, `B → blue`, `Gy → grey/gray`, and for Bro
   `H → hammer`, `F → fire`, `B → boomerang`. The resolver generates `redtoad`,
   `toadred`, `rtoad` and `toadr` for every variant. That covers most of today's 264
   rows, so the data file shrinks to the codes and nicknames people actually invented.
4. **A family name has a declared default variant.** Each multi-variant family names
   its default in the data file (the table above), exposed as
   `CharacterFamily.KOOPA.default -> Character.KOOPA_R`. `Character.parse("koopa")`
   returns that default. `CharacterFamily.parse("koopa")` returns the family, which is
   what a caller wants for totals across variants (RioBot's `!stats toad`). The default
   is stated once, as data, rather than falling out of row order.
5. **Misses suggest.** `UnknownNameError` (a `UnknownCodeError`, so also a `ValueError`)
   carries `.suggestions`, computed with stdlib `difflib.get_close_matches` over the
   normalised names. There's no dependency.
6. **The data is keyed, commented and shared.** `pyrio/_data/nicknames.toml` is read with
   stdlib `tomllib` (Python 3.11+), lazily on the first `parse` call:
   ```toml
   [characters]
   "Toad(B)"  = ["bt", "teardrop"]     # keyed by canonical label, never by row
   "Koopa(G)" = ["gk", "greg"]
   [families]
   "Koopa"     = { default = "Koopa(R)", nicknames = ["koopa"] }
   "Magikoopa" = { default = "Magikoopa(B)", nicknames = ["mag", "magikoopa"] }
   ```
   It's a file a non-programmer can send a PR to. RioBot's 122 extra nicknames are
   merged in once, and then the bot deletes its copy.
7. **Tests guard the data.** Every key must be a real label. No normalised name may
   resolve to two characters, or to both a character and a family, unless it's declared
   as a family name. Generated variant forms must not collide with curated nicknames.
   Every multi-variant family must declare a default. This is how a conflict like `pt`
   or `bb` gets caught and decided once, in review, as it was here.
8. **Other types use the same pattern where people type them.** `Stadium.parse("bc")`
   and `Stadium.parse("toy")` work the same way. Results, positions and swing types only
   need the strict constructor, plus argparse/CLI choices built from the labels.

**One content call to make:** everything in `nicknames.toml` ships in a public package
and is reachable through the API. Review once whether every community nickname
(e.g. `pisswizard`) belongs in the shipped data, or in a bot's own small dict that it
checks before calling `parse`.

## 3. Stat files → a typed game model

### Target

```python
import pyrio
from pyrio import Character, AtBatResult, Side

game = pyrio.read_game("decoded.json")        # path, file object, or dict via Game.from_dict
game.id, game.version, game.started_at        # int, Version, datetime
game.stadium                                  # Stadium.BOWSER_CASTLE
game.result                                   # GameResult(winner=Side.HOME, is_mercy=False, quit_by=None)
game.home.player, game.home.score, game.home.captain
game.team(Side.AWAY)

for spot in game.away.roster:                 # tuple[RosterSpot, ...], index == roster spot
    print(spot.character, spot.batting.ops, spot.pitching.era)
game.away.batting                             # BattingLine summed over the roster

homers = [e for e in game.events
          if e.batter is Character.MARIO and e.result is AtBatResult.HR]
event.state.outs, event.state.runners         # GameState snapshot at the pitch
event.pitch.type, event.contact.vertical_angle, event.fielding.bobble, event.runners[1].steal
```

### Model

Frozen, slotted dataclasses: `Game`, `Team`, `RosterSpot`, `BattingLine`,
`PitchingLine`, `Event`, `GameState`, `Pitch` (`None` when there was no pitch),
`Contact` (`None` when there was no contact), `Fielding`, `Runner` and `GameResult`.
Every coded field is an enum, and every optional section is `X | None` rather than an
empty dict.

- **`Side` replaces `team_num`.** The decoder applies the 1.9.2 home/away flip once, so
  the footgun is gone from the public API. No caller ever needs to know which era a file
  came from.
- **The decoder is version-aware** and owns every per-version rule: the home/away flip,
  the old team structure, hex vs decimal `GameID`, the 5/6 label swap, renamed keys and
  missing fields. This is `docs/version-decoding-proposal.md`, adopted as the only place
  version logic lives. `Version` is a comparable tuple type, replacing string lists and
  `versionBefore`.
- **Encoded files are the source of truth.** The decoder reads encoded ids and gets
  labels from the enums, so pyrio no longer needs decoded files. Encoded ids are also
  unambiguous: the 5/6 swap shows that decoded labels shift between versions. Decoded
  files still parse, by accepting labels for every coded field, while they're still
  being written. That also fixes today's `KeyError: 2` when building `EventSearch` from
  an encoded file. For a human-readable view, a `pyrio decode FILE` console script
  prints one on demand.
- **Structure follows the game.** `game.half_innings` yields `HalfInning(inning, half,
  batting: Side, events, runs)`. `event.state.bases` is a `Bases(Flag)`
  (`FIRST | THIRD`, whose `str()` is `"1-3"`). `event.batter_spot` and
  `event.fielding.spot` are `RosterSpot` objects, which are hashable, so they work as
  dict keys. `Runner.scored` is a bool. Today's callers rebuild each of these by hand.
- **Candidate: `Game.pitcher_of_record` / `winning_pitcher`.** League Tools derives it
  from lead changes for fantasy scoring. It passes the "would a second tool want this"
  test, and the rule is well defined.
- **Serialization.** `pyrio.to_jsonable(obj)` turns any model into plain
  dicts and lists, with enums as labels, for web front ends such as RioVisualizer's.
- **HUD files decode into the same types** (`Team`, `RosterSpot`, `Runner`,
  `GameState`), wrapped in a `HUDSnapshot`. The caller passes the producing version
  (`read_hud(path, version=...)`), which closes the HUD 5/6 ambiguity.
- **Derived stats live on the lines:** `BattingLine.avg/obp/slg/ops/k_pct` and
  `PitchingLine.era/innings_pitched/k_pct/avg_against` are properties computed in
  `_stats.py`. There's one formula per stat, so the conflicting `StatObj.obp` and
  `slg`, and the ERA that counted all runs, all go away.
- **Renamed fields are decoder rules too.** Clients 0.1.6–1.9.1 wrote
  `"Pitches Per Position"`. 1.9.2 renamed it `"Batters Per Position"` and changed the
  count from pitches to batters (ProjectRio `ee757054f4`). Each per-version key is a
  decoder rule with a test, and the field-parity test lists legacy keys explicitly in
  `_LEGACY_FIELDS`, with the release that dropped each one.

### `EventSearch` is deleted

Its 73 methods are prebuilt indexes over roughly 200 events, which a list comprehension
scans in microseconds. Filtering is plain Python over `game.events`. The few facts it
computed that aren't simple field reads become properties: `Event.is_first_pitch`,
`Event.is_last_pitch`, `Event.is_hit`, `GameState.leader`, `Game.lead_changes`,
`Game.walkoff`. For analysis across many games,
`pyrio.pandas.frame(e for g in games for e in g.events)` gives a DataFrame.

### Also deleted

`StatObj`, `EventObj`, `HudObj`, `RunnerObj`, `EventSearch`, `ErrorChecker`, the
`stat_file_parser.py` shim, and the camelCase names (all 121 of them).

## 4. Web client

### Target

```python
from pyrio.web import RioClient

with RioClient.from_env() as rio:                      # or RioClient(api_key=...)
    games = rio.games(tags=["Stars Off"], limit=100)    # list[GameSummary]
    stats = rio.stats(users=["MattGree"], by_character=True) # list[StatRow]
    rio.communities.create(name="...", private=True)
    rio.tags.list(), rio.tag_sets.ladder("S13 Superstars Off")
```

- **Installed with `pip install 'projectrio[web]'`** (section 7a).
- **Provisional in 1.0.** Rio web 2.0 reworks tag sets, communities and the game's
  player columns, so `pyrio.web` may change in a minor release until that API settles
  (section 7b). The core carries the full 1.0 promise.
- **httpx-style lifecycle.** The client is a context manager owning one session, with a
  default timeout. Today there's no timeout at all, so a stalled server hangs the
  caller. Retries with backoff apply to idempotent GETs.
- **An async twin, `AsyncRioClient`**, with the same methods, as python-chess offers for
  its engine API. RioBot runs inside discord.py's event loop and calls blocking
  `requests.get` in every command, so one slow API response freezes the whole bot.
- **Explicit credentials.** `RioClient(api_key=...)` reads nothing implicitly.
  `RioClient.from_env()` is the one place that reads `PYRIO_API_KEY`. Reading
  `rio_key.json` from the working directory goes away: a library shouldn't pick up
  files based on where it was launched. A missing key isn't printed at construction.
  Calling an authed endpoint without one raises `AuthenticationError`.
- **Real signatures.** Each endpoint takes keyword-only typed arguments, using enums
  where the API takes coded values (`characters=[Character.MARIO]`). Unknown arguments
  become a `TypeError` for free. Today `get_games("tag")` silently returns unfiltered
  data, and unknown kwargs pass through to the server. The `ParameterList` classes, the
  `params | dict | **kwargs` triple path and `_serialize_params` go away. `api.Endpoint`
  becomes private.
- **Typed results.** Responses decode into frozen dataclasses, reusing the section 2
  enums. See section 4a.
- **Resource namespaces.** Management endpoints group under `rio.communities`,
  `rio.tags`, `rio.tag_sets`, `rio.users` and `rio.keys`, instead of 30 flat
  `community_*` / `*_tag` methods.
- **Explicit caching.** `CompleterCache` becomes an optional
  `RioClient(cache=DiskCache(path))`, defaulting to no cache. No `print` on update.
- `LandingData` (a DataFrame wrapper with `get_*` methods in `api.py`) is deleted.
  `rio.landing_data()` returns `LandingRow`s, and `pyrio.pandas.frame()` handles them.
- **Open question, needs one live call:** `_strip_value` removes internal whitespace, so
  `captain="Baby Mario"` goes out as `"BabyMario"`. Enum-typed arguments make this moot
  for coded values, but confirm what the API expects for free-text fields.

## 4a. Converting web responses

### What happens today

Each `get_*` method returns a DataFrame by default, or the raw JSON dict with `raw=True`.
Each endpoint has its own conversion code. These are all reproduced against responses
shaped like ProjectRio-web's own route code (`d4bf233`):

- **Two endpoints always return an empty DataFrame.**
  - `/events/` returns `{game_id: {event_num: event_id}}`, but `get_events` looks for
    an `"Events"` or `"events"` key.
  - `/star_chances/` returns `{"Data": [...]}`, but `get_star_chances` looks for
    `"Star Chances"` or `"star_chances"`.

  Both fall back to `[]` when the key is missing, so a wrong guess looks exactly like
  "no results".
- **`get_games()` makes four HTTP calls and writes to disk.** Resolving the
  `game_mode` id to a name builds a `CompleterCache` behind the scenes. That calls
  `/tag/list`, `/user/all/` (every user on the site) and `/tag_set/list`, then writes
  `cache/cache.pkl` **into the current working directory**. Next time it loads it back
  with `pickle`, which runs code from whatever file sits at that path.
- **Conversion stops halfway.** `stadium` becomes a name string, not a `Stadium`.
  Captains stay strings and rosters stay lists of raw char ids. Timestamps are converted
  to a hard-coded **US/Eastern** timezone. The Elo fields, linescore and scoring plays
  pass through untouched.
- **Stats become columns named after the server's keys,** such as
  `Batting_summary_at_bats`, through a flattener that has to be told the request's
  `by_*` flags to know how deeply the response is nested. Callers then recompute
  AVG/OBP/ERA themselves (RioBot does it twice, with formulas that differ from pyrio's).
- **One method, two return types** (`Union[pd.DataFrame, dict]`). A type checker
  can't tell you which one you got.

- **Requests are wrong too, not just responses.** Checked against the server's route
  code:
  - **Flags never reach the server.** pyrio sends Python bools, which encode as
    `"True"`, but the server tests `== '1'`. Every `by_*`, `exclude_*` and `include_*`
    flag on `/stats/` and `include_linescore` on `/games/` is silently off, and
    `_process_stats` then flattens a nesting the server didn't produce.
    `limit_games=True` gets a 400.
  - **Parameter names the server never reads.** `landing_data` sends `event_list` and
    `game_list`, but the server reads `events` and `games`. `/tag/list` sends
    `community_ids`, but the server reads `Communities`. `/games/` sends
    `include_teams`, and `/manual_submit_game/` sends `recalc`; neither is read.
  - **Inherited filters that are silently dropped.** `StatsParameterList` subclasses
    `EventsParameterList`, so it offers `pitcher_char`, `contact`, `inning` and more,
    none of which `/stats/` reads.
  - **Types the server rejects.** `/tag/list` sends `Types` as a string, but the server
    expects a list. Tag-set `start_date`/`end_date` are typed `str`, but the server
    stores ints.
  - **Accepted, but pyrio can't send them:** `include_scoring_plays` on `/games/`, and
    `home_score`/`away_score` on `/events/`.
  - **Useful reads that aren't wrapped:** `/characters/` and `/ladder/games/`.

  Typed keyword-only signatures (section 4), one encoding table for the server's
  conventions (`'1'` for flags), and the contract tests below catch every one of these.

### Target

One private module, `web/_decode.py`, the web counterpart of the stat-file decoder. It
is the only place server JSON keys appear, with one function per endpoint, each
returning frozen models:

```python
games = rio.games(tags=["S13 Superstars Off"], limit=50)     # list[GameSummary]
g = games[0]
g.stadium                     # Stadium.MARIO_STADIUM
g.ended_at                    # datetime, UTC-aware; convert with .astimezone(...) yourself
g.home.captain, g.home.roster # Character, tuple[Character, ...] indexed by roster spot
g.home.score, g.result.winner # 5, Side.HOME
g.tag_set_id                  # 42 -- an id; naming it is an explicit call, see below

rows = rio.stats(users=["MattGree"], characters=[Character.MARIO], by_character=True)
rows[0].character             # Character.MARIO  (grouping keys are typed, None when not grouped)
rows[0].batting.ops           # BattingLine -- the same class stat files produce
rio.stats(..., by_swing=True)[0].batting_by_swing[SwingType.STAR].avg

rio.event_ids(...)            # list[EventRef(game_id, event_num, event_id)]
rio.star_chances(...)         # list[StarChanceRow]
rio.landing_data(...)         # list[LandingRow] with ContactType, Hand, ... decoded
```

Rules:

1. **Decode fully, once.** Every coded field becomes its enum, every timestamp a
   UTC-aware `datetime`, every roster a tuple of `Character`. Optional sections
   (`linescore`, `scoring_plays`, Elo) are typed `X | None`. The library never picks a
   display timezone.
2. **Never guess a key.** No `get("Events", get("events", []))`. A missing required key
   raises `APIResponseError(APIError)` naming the endpoint and the keys that were
   present. Both empty-DataFrame bugs would have raised on the first call. *Unknown
   extra* keys are ignored, so the server can add fields without breaking clients.
3. **One stats model whatever the flags.** The `by_*` nesting is walked once, in the
   decoder, into flat `StatRow`s. Grouping keys (`game_id`, `user`, `roster_spot`,
   `character`) are present or `None`. Lines (`batting`, `pitching`, `fielding`,
   `misc`) reuse `BattingLine` and `PitchingLine`, so web stats and stat-file stats have
   the same fields and the same formulas. Server names like `summary_at_bats` map to
   `at_bats` in exactly one table.
4. **No hidden calls, no hidden files.** A request makes one HTTP call. Reference data
   is explicit: `rio.tag_sets.list()`, `rio.tag_sets.get(42)`, `rio.users.list()`.
   With an opt-in `cache=DiskCache(path, ttl=...)`, those calls are served from JSON
   (never pickle) at a path the caller chose. Nothing is ever written to the working
   directory.
5. **One return type per method.** Models only. DataFrames come from
   `pyrio.pandas.frame(games)`, a single flattener driven by the models' fields, with
   enums as labels in categorical columns. That replaces the per-endpoint processors and
   gives consistent column names. For an endpoint pyrio doesn't model yet, the escape
   hatch is one method, `rio.request_json("GET", "/path/", params=...)`, instead of a
   `raw=` flag on every method.
6. **Contract tests.** Recorded responses for each endpoint live in `tests/fixtures/web/`,
   captured once from the live API and stripped of user data. The decoders are tested
   against them under `respx`. A scheduled job (not a PR check) replays the same
   read-only public queries against the live API and fails if a response no longer
   decodes. That's how server-side drift gets noticed before users hit it.

## 5. Simulation and geometry

- **One stadium geometry module, `pyrio.geometry`**, built from the collision meshes.
  It provides walls, fences, hazards, fielder starting positions, the lockout table and
  boundary polygons. Every function takes a `Stadium`. Today `stadiums.is_home_run` and
  `live_ball.is_home_run` are two functions with the same name and different methods.
  Keep one, and if both answers are useful, name them for what they compute. The
  duplicated physics constants (`GRAVITY`, `DRAG` / `AIR_RESISTANCE`), fielder tables,
  lockout tables, stadium→file maps and five polygon parsers each collapse to a single
  definition.
- **`HitInputs` is typed with the enums:** `batter: Character`, `pitcher: Character`,
  `pitch: PitchType`, `charge: ChargeType | None`, `swing: SwingType`, `hand: Hand`,
  `stick: InputDirection`. The packed 0–4 `pitch_type_val` and the four-way swing
  spelling go away. Star inputs are what a player controls, `stars: int` and
  `is_captain: bool`, and the library resolves the star-swing type, captain or
  non-captain, and Moonshot. RioVisualizer currently reimplements that resolution in
  `_resolve_star`. The gecko-mod booleans become `mods: frozenset[Mod]` with
  `Mod(Enum)`, and `TAG_TO_MOD` maps API tags to it.
- **One constructor and one entry point per job.** `HitInputs.from_event(event, mods=...)`
  replaces `hit_inputs_from_event` and `_inputs_from_event`. That leaves
  `simulate_hit(inputs)`, `simulate_trajectory(inputs, frames)` and
  `simulate_all_zones(inputs)`. The `*_from_event` and `*_from_landing_row` variants go
  away.
- **`HitResult` uses enums:** `contact_type: ContactType`, not
  `contact_type_name="Left Sour"`.
- **`live_ball` options become keyword-only parameters**, or a frozen `LiveBallOptions`.
  `continue_ball(..., hazard=False)` currently runs with hazards *on*. It stays
  stdlib-only and parity-checked against RioVisualizer.
- **`hit_analysis`:** `ContactRecord` is typed with `batter: Character`, and highlights
  come back as a `Highlights` dataclass. Text formatting is a separate function, and
  `hardest_hit` / `longest_flight` / `highest_apex` become a single `best(contacts, key)`.
- **`hit_sim_validation` is a developer tool.** It moves to `tools/` and isn't shipped.

## 6. Everything else

- **Ratings.** `glicko2.py` and `glicko_calculator.py` merge into `pyrio.ratings`. A
  frozen `Rating(rating, rd, volatility)`, a pure `update(rating, results) -> Rating` and
  `win_probability(player, opponent)`. No `getRating` / `setRating`, no mutable `Player`, no `main()`.
  **The parameters are the server's**, because Rio web runs the official ladder: tau
  0.5 and a starting RD of 300 (`app/glicko2.py:29`, `app/consts.py:43-45`). pyrio has
  tau 1.2 and RD 350 today, so ratings computed with pyrio don't reproduce the site's.
  pyrio keeps the 2012 bisection step for volatility, which converges where Rio web's
  exact-equality Newton loop can spin. A test pins `update` against ratings recorded
  from the server, so Rio web can adopt `pyrio.ratings` with no change in numbers
  (section 11).
- **Team names.** `team_name_algo.py` becomes the private `_team_names.py`, exported as
  `pyrio.team_name` (section 7). It's already the template the rest should follow. Keep `CAPTAIN_TEAMS` public: per the "programmatic
  wiki" principle, domain data is a deliverable, not an implementation detail.
- **Formatters.** The `stat_formatters` free functions go private, behind the
  `BattingLine` / `PitchingLine` properties. Loose numbers go through the line:
  `BattingLine(hits=3, at_bats=10).avg`. That ends the `**_` swallow, where today
  `batting_avg(hit=3, at_bats=10)` silently returns `0.0`. Properties return unrounded floats, with `math.nan` for a zero
  denominator. Rounding and `.333`-style display belong to `format_*`.
- **Rendering.** `draw/` becomes `pyrio.svg` (stadium outline, fielders, spray chart,
  returning SVG strings, no dependencies, like `chess.svg`) and `pyrio.plot` (matplotlib
  adapters, behind the `plot` extra). The commented-out code and duplicated data go
  away.
- **`helpers.py` is dissolved.** Fielder geometry moves to `pyrio.geometry`. The
  DataFrame distance and speed calculations move to `pyrio.pandas`, or out of the
  library if only one downstream tool uses them.
- **`examples/`** is rewritten against the new API and executed in CI so it can't rot.
  Today `game_summary.py` silently skips the stadium outline, because it looks up a
  `Stadium` in a name-keyed dict.

## 7. Package shape

### The rule

python-chess and httpx between them settle the shape.

- **`import pyrio` is the core**, like `import chess`. It holds the game's vocabulary
  (every enum, `Character`, `CharacterFamily`), the game model, reading stat files and
  HUDs, and the core errors. A stat-file user needs one import, and every core name has
  exactly one public spelling: `pyrio.X`.
- **Each separate job is a public submodule imported by name**, like `import chess.pgn`
  or `import chess.engine`: `pyrio.web`, `pyrio.sim`, `pyrio.geometry`, `pyrio.ratings`,
  `pyrio.svg`, `pyrio.plot` and `pyrio.pandas`. `import pyrio` imports none of them. That
  keeps the core import cheap, and it's what makes the extras genuinely optional, since
  nothing can load `pyrio.pandas` by accident.
- **Every other module is private**, as in httpx (`httpx/_client.py`, `_models.py`, all
  re-exported from `httpx`). The core lives in `_codes.py`, `_game.py` and so on, and is
  reached only as `pyrio.Character`, never `pyrio._codes.Character`. Files can then be
  split, merged or renamed after 1.0 without a major version. The previous draft of this
  section had public `codes.py`, `game.py` and `stats.py` *and* re-exported them from
  `__init__`, which gave every name two spellings.

### Layout

```
src/pyrio/
  __init__.py        # the core's public API: explicit __all__, re-exports only, no logic
  __main__.py        # `pyrio decode FILE`, also `python -m pyrio` (argparse)
  py.typed
  _enum.py           # CodeEnum: __new__, _missing_, .id/.label, ordering
  _codes.py          # Stadium, PitchType, AtBatResult, ... (~20 enums); Side, Bases, InputDirection
  _characters.py     # Character, CharacterFamily, CharacterAttributes, CharacterClass, Ability
  _names.py          # normalise(), the parse() resolver, suggestions
  _stats.py          # BattingLine, PitchingLine (+, derived properties), format_*
  _game.py           # Game, Team, RosterSpot, Event, GameState, Pitch, Contact, ..., Version
  _decode.py         # version-aware stat-file/HUD decoder: read_game, read_hud, iter_games
  _serialize.py      # to_jsonable
  _team_names.py     # team_name(), CAPTAIN_TEAMS
  _errors.py         # RioError, UnknownCodeError, UnknownNameError, StatFileError
  _data/             # character_attributes.csv, nicknames.toml
  geometry/          # walls, fences, hazards, fielder positions, lockouts, boundary polygons
    __init__.py
    _mesh.py, _fielders.py, ...
    _data/           # collision/*.json.gz + MANIFEST.json, parks/*.park.json, outlines
  sim/               # simulate_hit, simulate_trajectory, simulate_all_zones, live ball, analysis
    __init__.py
    _hit.py, _tables.py, _live_ball.py, _analysis.py
  web/               # RioClient, AsyncRioClient, DiskCache, response models, HTTP errors
    __init__.py
    _client.py, _async_client.py, _resources.py, _models.py, _decode.py, _cache.py, _errors.py
  ratings.py         # Rating, update, win_probability
  svg.py             # stdlib-only rendering, returns str
  plot.py            # matplotlib adapters      [extra: plot]
  pandas.py          # frame()                  [extra: pandas]
```

### Decisions behind it

1. **Characters get their own module.** `Character` is the richest type in the library:
   attributes, family, parsing. Today `rio_value` and `constants/character_data` import
   each other, and a lazy import inside `Character.attributes` hides the cycle.
   Putting `Character`, `CharacterFamily` and `CharacterAttributes` together in
   `_characters.py` removes the cycle instead of hiding it. `_codes.py` holds the other
   enums. `_names.py` holds the resolver that `Character.parse`, `CharacterFamily.parse`
   and `Stadium.parse` share.
2. **Imports flow one way, and a tool checks it.**
   ```
   _errors <- _enum <- _codes, _characters, _names <- _stats <- _game <- _decode   (core)
   core <- geometry <- sim        core <- web (+ httpx)        geometry <- svg <- plot
   ```
   The core imports no submodule. `geometry` imports only the core. `sim` imports
   `geometry` and the core. `web` imports the core and httpx. `Stadium` knows nothing
   about meshes: geometry functions take a `Stadium`, not the other way round. An
   [import-linter](https://import-linter.readthedocs.io/) layers contract runs in CI, so a
   cycle like today's can't come back.
3. **Errors live with the code that raises them, under one base.** `RioError` and the
   lookup and stat-file errors are core (`pyrio.StatFileError`). The HTTP errors live in
   `pyrio.web`: `APIError`, then `AuthenticationError`, `NotFoundError`,
   `APIResponseError`, and `APIConnectionError` with
   `APITimeoutError(APIConnectionError, TimeoutError)` beneath it (names per section 7b,
   rule 11). Those last two wrap
   httpx's transport errors, so callers never import httpx just to catch a failure (the
   pattern the httpx-based OpenAI and Anthropic SDKs use). `except pyrio.RioError` still
   catches everything the library raises on purpose. The core knows nothing about HTTP.
4. **A single file where a package would be ceremony.** `ratings`, `svg`, `plot` and
   `pandas` are one file each. `geometry`, `sim` and `web` are packages because they have
   several parts, and two of them carry data. Turning a module into a package later
   doesn't change its import path.
5. **Team names fold into the core.** `pyrio.team_name(roster)` returns a `TeamName`,
   which is a core enum, so a separate public module would hold one function and one
   table. `CAPTAIN_TEAMS` stays public at top level (programmatic wiki).
6. **Data sits beside the code that reads it**, in a `_data/` folder: core data in
   `pyrio/_data/`, meshes in `pyrio/geometry/_data/`. It loads through
   `importlib.resources.files(...)`, lazily on first use, behind `functools.cache`.
   `CharNames.csv` is deleted: the enum holds ids and labels, and `nicknames.toml` holds
   what people type. The folder is `_data`, not `data`, because `.gitignore` ignores every
   directory named `data/`.
7. **`pyrio.pandas` has one entry point, `frame(items)`.** It flattens a sequence of any
   one model type (`Event`, `GameSummary`, `StatRow`, `LandingRow`, `ContactRecord`),
   driven by the dataclass fields, with enums as categorical labels. `Event` carries
   `game_id`, so `frame(e for g in games for e in g.events)` keeps it. Per-type
   `*_frame()` functions, `LandingData` and `decode_columns` aren't needed. The module is
   named after its extra, mirroring `pip install 'projectrio[pandas]'`. Inside it,
   `import pandas` still means the real pandas, because absolute imports never pick up a
   sibling module.
8. **The CLI ships in the package.** `[project.scripts] pyrio = "pyrio.__main__:main"`,
   built on argparse with no click. 1.0 has one subcommand, `decode`.
   `hit_sim_validation` is a developer tool and moves to `tools/`, which never ships.
9. **One version source.** `version` lives in pyproject, and
   `pyrio.__version__ = importlib.metadata.version("projectrio")`.

### Build and packaging

- **Build backend: hatchling**, the PyPA tutorial's default. It ships every file under
  `src/pyrio/` automatically, which replaces today's hand-kept `package-data` globs. A
  glob forgotten there fails no test, because tests run from the source tree.
- **CI tests the wheel, not the checkout.** Build the sdist and wheel, run `twine check`,
  install the wheel into a clean venv and run the suite against it. That's the only check
  that catches a data file missing from what users actually install.
- **The public surface is pinned.** `pyright --verifytypes pyrio` requires every public
  symbol to be fully typed. `tests/test_public_api.py` snapshots each public namespace's
  `__all__`, so adding or removing a public name shows up as a diff in review.
  That's how "adding something to `__init__` is a commitment" gets enforced.
- **Import cost is tested.** After `import pyrio`, none of `httpx`, `pandas`, `numpy` or
  `matplotlib` is in `sys.modules`, and no data file has been opened.
- **Outside the package:** `tools/`, `examples/`, `docs/` and `tests/`. `tests/` mirrors
  the public namespaces (`tests/web/`, `tests/sim/`, ...) and shares `tests/fixtures/`.
  `requirements.txt` is deleted.
- **Python:** require **≥ 3.11**. 3.10 reached end of life in October 2026, and 3.11
  brings `Self`, `StrEnum`, `tomllib` and `enum` improvements.

### Import name: `pyrio` (decided)

The import name stays `pyrio`, and the distribution stays `projectrio`. This was
reconfirmed on 2026-11-21, knowing about the clash: `pip install pyrio` installs
[kaliv0/pyrio](https://github.com/kaliv0/pyrio), an unrelated library that also installs
a top-level `pyrio` package. So the install command has to be impossible to miss.
The README opens with `pip install projectrio`, the package docstring and the docs home
page say it too, and `pyrio.__version__` reads the `projectrio` distribution's metadata.

## 7a. Dependencies

**Today:** pandas, numpy, scipy, matplotlib and requests are all mandatory. That's
about **235 MB** installed, of which requests is 1 MB. Anyone who only wants characters
and stat files, or a Discord bot that only calls the API, downloads a scientific stack.
`requirements.txt` adds pytz, requests_cache and SQLAlchemy, none of which anything
imports. At runtime pandas is already imported lazily (`import pyrio` loads only
requests, in about 150 ms), so the cost is almost entirely at install time, and it
falls on every downstream tool.

**Target:**

```toml
[project]
dependencies = []

[project.optional-dependencies]
web    = ["httpx>=0.27"]
pandas = ["pandas>=2.0"]
plot   = ["matplotlib>=3.7"]
all    = ["projectrio[web,pandas,plot]"]

[dependency-groups]
dev = ["pytest", "pytest-cov", "respx", "ruff", "pyright", "import-linter", "build", "twine"]
```

**Why httpx is an extra, not core.** An earlier draft made httpx the one core
dependency. Rio web settled it (section 11): the server would use pyrio's decoder,
enums, stat lines and ratings, and never its client, so a core httpx would be installed
there for nothing. The same goes for every stat-file tool. Section 7 already made
`pyrio.web` a separately imported submodule, so making it an extra costs nothing:
`pip install 'projectrio[web]'`, and `import pyrio.web` without it fails with the same
clear `ImportError` as the other extras. The core then has no dependencies at all,
like python-chess.

What happens to each dependency:

| Dependency | Used today for | Plan |
|---|---|---|
| **scipy** (98 MB) | `ConvexHull` in `calculate_stadium_area`, and `griddata` in a demo block in `draw_stadium.py` | **Deleted.** Area becomes the shoelace formula over the stadium's boundary polygon (about 5 lines). That also fixes a bug: in 2-D, scipy's `ConvexHull.area` is the *perimeter* (a unit square gives `.area == 4.0`), so the function has never returned an area. The demo block is example code and goes to `examples/`. |
| **numpy** (33 MB) | `np.loadtxt` and array plumbing in `draw/`; vector math in `helpers.py` | **Not listed at all.** Polygon parsing moves to `pyrio.geometry`, as pure Python. The vectorised helpers move to `pyrio.pandas`, where numpy already comes with pandas. |
| **matplotlib** (33 MB) | `draw/` | **`plot` extra**, imported only inside `pyrio.plot`. Zero-dependency rendering is `pyrio.svg`. |
| **pandas** (71 MB) | DataFrame output from `rio_web` (5 places); `CompleterCache` (a DataFrame just to filter a tag list); `hit_analysis.contacts_to_dataframe`; the Series branch of `lookup()`; `helpers.py`; `LandingData` | **`pandas` extra**, imported only inside `pyrio.pandas`. That module holds `frame()` (section 7) and the fielder distance/speed helpers. The cache becomes plain lists and dicts. |
| **requests** | HTTP | **Replaced by httpx, behind the `web` extra**, imported only inside `pyrio.web`. A single library gives both `RioClient` and `AsyncRioClient` (section 4), applies timeouts by default, and is mocked in tests with `respx`. |

**Rules that keep it this way:**

1. **Extras live only in their own modules.** No core module imports httpx, pandas,
   numpy or matplotlib, even lazily. An extras module fails clearly at the top:
   `ImportError("pyrio.pandas needs pandas: pip install 'projectrio[pandas]'")`.
2. **Lower bounds, no caps.** Floors are the oldest versions CI actually tests, not
   whatever happened to be installed. Today's `matplotlib>=3.10.3` and `numpy>=2.2`
   force users to upgrade for no reason. Upper caps cause unsolvable conflicts in
   users' environments.
3. **CI enforces it.** A `core-only` job installs without extras and runs the suite.
   Extras tests use `pytest.importorskip`. A test asserts `import pyrio` leaves
   `httpx`, `pandas`, `numpy` and `matplotlib` out of `sys.modules`.
4. **`requirements.txt` is deleted.** pyproject holds runtime and extras dependencies,
   and the `dev` group holds tooling.

## 7b. Naming

Five surveys on 2026-11-21 covered every module and this plan. Most of today's bad names
die with the code that holds them: 118 of the 123 camelCase method definitions are in
`StatObj` and `EventSearch`, which section 3 deletes. So nothing is renamed in place. The
rebuild writes new names to the rules below, and the names elsewhere in this plan
already follow them.

### Rules

1. **PEP 8 case, no exceptions.** snake_case for functions, methods, attributes,
   parameters and modules; CapWords for classes; UPPER_SNAKE for module constants and
   enum members; a leading underscore for anything private. Acronyms are all caps in
   CapWords and lowercase in snake_case: `HUDSnapshot`, `APIError`, `game_id`, `read_hud`.
2. **One word per concept**, from the glossary below. A synonym is a bug. Today `walks`
   sits beside `battersWalked`, `chem_on_base` beside `chem_links_on_base`, and the
   batter's hand has three spellings in three classes.
3. **No type or noise affixes.** No `Obj`, `_dict`, `_json`, `_list`, `_df`, `_str`,
   `Data`, `Info`, `Helper`, `Util`, `Algo`, `Calculator` or `ParameterList`. No `get_`,
   `calc_`, `calculate_` or `return_` prefixes: data is a property, and work is a verb
   (`read_game`, `simulate_hit`). Two suffixes carry meaning and stay: `Line` for a stat
   line (`BattingLine`) and `Row` for one record of a flat web result (`StatRow`,
   `LandingRow`).
4. **Booleans read as yes or no:** `is_`, `has_`, `was_`, or a participle or adjective
   that answers one (`scored`, `caught`, `private`). A predicate returns a `bool`. Today
   `bool_runner_on_base` returns an `int` and `hexGameID` returns a bool with no
   predicate in its name.
5. **Collections are plural**, and so are parameters that take lists: `tags=`,
   `characters=`, `game_ids=`. Today the dataclass fields are `tag`, `username`,
   `pitcher_char` (all lists) beside `game_list` and `events`.
6. **Parameters don't shadow builtins:** `kind`, not `type` (today `comm_type`,
   `tag_type`, `game_mode_type`). An attribute may be `type`, as in `pitch.type`, since
   `obj.type` shadows nothing.
7. **Units are in the name when they aren't obvious:** `_frames`, `_per_frame`, `_rad`,
   and `_raw` for the game's angle units (4096 to a full turn). Each quantity has one
   default unit, documented on the type, and anything else carries a suffix. Today
   `GRAVITY`, `DRAG`, `power`, `apex` and `fielder_speed` give no unit.
8. **Abbreviate only where the domain does:** `id`, `rbi`, the rate stats (`avg`, `obp`,
   `slg`, `ops`, `era`, `whip`, `k_pct`, `iso`) and Glicko's `rd`. Counting stats are
   spelled out: `hits`, `at_bats`, `strikeouts`, `home_runs`, `walks`, `hit_by_pitch`.
   No `char`, `stad`, `pos`, `vel`, `loc`, `coord`, `desc`, `num` or `recalc`.
9. **Decompiled identifiers stay out of names.** The decomp is the reference, not the
   vocabulary: a name says what the thing does, and the symbol or address goes in a
   comment for cross-reference. `AtBat_MoonShot` becomes `is_moonshot`, and
   `SHORT_ARRAY_ARRAY_ARRAY_ARRAY_807b67cc` gets a name for what the table holds.
10. **Names read correctly where they're used.** Core names are reached as `pyrio.X`.
    Submodule names get imported bare (`from pyrio.web import RioClient`), so they mustn't
    collide with names a caller already has. That's why it's `RioClient`: RioBot already
    imports `discord.Client`.
11. **Only the base error carries the package name**, the pattern of the httpx-based
    Anthropic and OpenAI SDKs. Core: `RioError`, `UnknownCodeError`, `UnknownNameError`
    (an `UnknownCodeError`), `StatFileError`. Web: `APIError`, then
    `AuthenticationError`, `NotFoundError`, `APIResponseError`, and `APIConnectionError`
    with `APITimeoutError(APIConnectionError, TimeoutError)` beneath it. The `API`
    prefix keeps the last two from shadowing the builtin `ConnectionError` and
    `TimeoutError`.

### Rio web's vocabulary

Rio web 2.0 (`EXTENSIBILITY_SCOPING.md` §3, in ProjectRio-web) reworks the objects
`pyrio.web` wraps:

- **`TagSet` splits** into a **Ruleset** (one revision of an exact code set, recorded on
  each game) and a **Competition** (what a game counts toward: one set of standings or
  one final placement).
- **`Community` becomes a Collection**: a named group of competitions that can overlap,
  nest, carry ladders and have a landing page. Whether it keeps the name "Community" is
  that document's open Q5.
- **"Game mode" is reclaimed** for the community meaning (Stars Off, Stars On, Big Balla).
  It's a label on Rulesets, plus a Collection where it needs a page. It's no longer an
  entity.
- **New objects:** `Fixture` (the expected game), `CompetitionEntrant` and a
  competition-scoped `CompetitionTeam`.

What that means here:

1. **pyrio never calls today's TagSet a "game mode".** The word is about to mean
   something else, so the object is named for what it is. Stat files' `"TagSetID"`
   decodes to `Game.tag_set_id: int | None` (the client writes `-1` for none), and the
   web namespace is `rio.tag_sets`. Docstrings say it's what the client and site
   currently call a game mode.
2. **When 2.0 lands, pyrio takes its nouns unchanged**: Ruleset, Competition, Collection
   (or whatever Q5 settles), Fixture, Entrant. The library, the API and the site then say
   the same thing.
3. **`pyrio.web` ships as provisional in 1.0.** Its namespaces mirror an API that 2.0 is
   reworking: tag sets split, communities generalize, and `Game`'s two player columns
   may become a join table (Q12). The docs and CHANGELOG mark `pyrio.web` provisional,
   as the standard library does for new modules, so it can change in a minor release
   until the 2.0 API settles. The core (enums, model, decoder) isn't affected and
   carries the full 1.0 promise.
4. **`Team.player` stays singular**, since every stat file has one player per side. If
   the 2v2 mod's files carry more (Rio web's Q14), it becomes `players`. What the mod
   writes decides it.
5. **Stat names match the site.** The frontend's competition stats (`lib/compete/stats.ts`,
   from the NNL workbook) add ISO, OPS+, ERA−, K/BB and pitches per inning. As line
   properties they're `iso`, `ops_plus`, `era_minus`, `k_per_bb` and
   `pitches_per_inning`. Its ERA scales to the competition's innings (7 for NNL), while
   pyrio's hard-codes 27 outs, so `PitchingLine.era` takes the game length instead.

## 11. Rio web

Surveyed on 2026-11-21 against ProjectRio-web `security-hardening` at `d4bf233`. Rio
web doesn't import pyrio. It carries its own copies of the same data and formulas
(`app/consts.py`, `app/glicko2.py`, inline stat SQL), and they've drifted. Its
`EXTENSIBILITY_ROADMAP.md` already anticipates that pyrio "may be adopted here later".
Its 2.0 rework of tag sets, communities and game modes (`EXTENSIBILITY_SCOPING.md` §3)
shapes pyrio's names and makes `pyrio.web` provisional; see section 7b.

### What Rio web would use

pyrio's job on the server is **the shared decoder and vocabulary, not the client.**

- **Ingestion.** `process_game` (`app/views/populate_db.py`, about 475 lines in one
  function) indexes the stat file directly, so one missing key fails the whole game,
  and it applies no version rules. With pyrio, ingestion becomes `game = read_game(data)`,
  then mapping the model onto rows. The version rules then live in one place for every
  Rio tool, server included. Each of these is confirmed in the code:
  - **GameID** is parsed as hex for every version (`populate_db.py:221`). Rio web's own
    2.1.1 test file has the decimal id `"1,189,820,580"`, matching its filename
    `..._1189820580.json`, so files from before 2.3.0 are stored under the wrong id.
  - **No home/away flip.** The version gate rejects only 1.9.0–1.9.4, so 0.1.x through
    1.9.1 files are accepted, and their team numbers are stored unflipped.
  - **The old `Team N Roster M` layout** raises a KeyError, which `process_game`'s
    blanket `except Exception` logs, and the game is never ingested.
- **Stat lines.** Rio web's `calculate_era` (`app/util.py:3`) gives runs per inning:
  no ×9, all runs rather than earned runs, and `-runs` as a sentinel when there are no
  outs. Its OBP leaves sacrifice flies out of the denominator. `BattingLine` and
  `PitchingLine` give the site, the bots and the tools the same numbers.
- **Ratings.** `pyrio.ratings` adopts the server's parameters (section 6), so the server
  can import it with no change in numbers.
- **Enums.** Rio web stores stadiums, results, positions, bobbles and the rest as bare
  ints with no labels. `games.py` has a TODO for stadium names. The section 2 enums
  supply labels, and its unused `cPLAY_RESULT_*` table (which has wrong labels, such as
  0x10 "ClearedBases" for a foul catch) can be deleted.

What the server **doesn't** use: `pyrio.web`, `pandas` or `plot`. That's why httpx is an
extra (section 7a).

### Constraints

- **Python.** Rio web runs Python 3.9 with Flask 2.0 and SQLAlchemy 1.4. Its move to
  Python 3.12, Flask 3 and SQLAlchemy 2 is decided (`EXTENSIBILITY_SCOPING.md`) but not
  done. pyrio needs ≥ 3.11, so adoption follows that upgrade. The two fit together:
  Rio web's ingestion hardening (`CLAUDE.md`, one transaction per `process_game`) and
  pyrio's decoder can land as one change.
- **Pinning.** Rio web pins an exact pyrio version, the way its roadmap already plans to
  pin pybracket, and upgrades on its own schedule.

  gone at 1.0. Point it at `MSB_StatTracker.h` and the pyrio enums instead.

### The API contract

`pyrio.web`'s decoder (section 4a) can absorb all of these, but every one fixed on the
server shrinks it, and all of them confuse anyone writing a client. They belong with
`docs/schema-sync-proposal.md` as a shared contract.

- **Booleans are written four ways:** `'1'` (games, stats, events), `t`/`True`/`true`
  (`Active`, `by_inning`), a `False`/`false`/`f` sentinel (`limit_games`), and
  `yes`/`y`/`true`/`t` (`Client`).
- **Key casing is mixed:** `games`, `Stats`, `Data`, `Tags`, `Tag Sets` (with a space),
  `Tag Set` (singular, holding a list), `users`, `ongoing_games`. Body keys mix
  `Email`/`TagSet`/`Rio Key` with `community_name`/`tag_set_id`.
- **Shapes vary:** bare dicts keyed by id or username (`/user/all/`, `/events/`,
  `/tag_set/ladder/`), a bare list (`/community/key`), and bare `'Success'` strings
  from the update routes.
- **Errors** are Werkzeug HTML pages, because no error handler is registered. Status
  codes are reused for different things: 409 means both not-found and conflict, 408 a
  bad time range, and 405 banned. Some 200 responses carry errors.
- **Credentials in query strings** on `/validate_user_from_client/` and `/populate_db/`.
- **Reference data:** there's no stadium route and no route for the coded-value tables.
  `/characters/` returns `captain` as the string `'True'`/`'False'`.
