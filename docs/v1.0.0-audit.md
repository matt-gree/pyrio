# v1.0.0 readiness audit

Six parallel scans across `src/pyrio`, `tests/` and `tools/` (~11.4k lines), looking for
inconsistencies, verbosity, and places the value-object construct from `rio_value.py`
should be applied. Findings marked **✓** were reproduced directly; the rest are reported
with a file:line citation but not independently run.

---

## 1. The verdict on cutting 1.0.0

`pyproject.toml:4` already says `1.0.0`. Cutting it as-is would freeze:

- **119 camelCase public methods** ✓ — 71 on `EventSearch`, 44 on `StatObj`, 4 on
  `glicko2.Player` (`getRating`/`setRating`/`getRd`/`setRd`, exported as `GlickoPlayer`).
  Plus camel keyword parameters used across the stat-file surface (`teamNum` appears 307
  times, `rosterNum` 206), `StatObj.statJson`, `EventObj.rioStat`/`eventDict`,
  `EventObj.result_of_AB`, `userInputToCharacter`, and the public typo
  `first_fielder_maunual_selected` (`stat_file/event.py:436`).
- **A string-sentinel error contract.** `lookup()` is exported and returns
  `"Invalid ID or Name: ..."` on a miss instead of raising ✓.
- **Derived stats that disagree with `stat_formatters`** ✓ — `StatObj.obp` is `(H+BB)/AB`
  while `stat_formatters.on_base_pct` is `(H+BB+HBP)/(AB+BB+HBP+SF)`. `slg` divides by
  `AB-BB` vs `AB`. `era` uses all runs vs earned runs. The `StatObj` versions also raise
  `ZeroDivisionError` where the formatters return `0.0`. **Fixing these changes numbers**,
  so this is the last window before a major bump.
- **A value-object construct that is half-applied and fails silently** (section 2).

### Recommendation

Don't cut 1.0.0 on the current surface. Two viable paths, in order of preference:

**(a) Shrink the public surface first, then cut.** CLAUDE.md already says "the top-level
`__init__.py` is the public API. If it's not re-exported there, treat it as internal."
That rule is the lever, and it already exists. Pare `__init__.py` down to what you intend
to support, state in the README that everything else is internal and may move, and cut
1.0.0 on that. You then owe compatibility on a surface you chose, not on 119 inherited
camelCase names. Removing exports later is breaking; removing them now is free.

**(b) Cut `1.0.0rc1`**, land the breaking fixes in section 4, then `1.0.0`.

Either way, two housekeeping items are worth doing in the same pass: there is no CI ✓
(no `.github/`), and CLAUDE.md's "Testing, releases, contribution" section claims there
are no tests while `tests/` holds 121 test functions ✓.

## 2. The big idea: finish the construct, don't just extend it

This is the direct answer to "are there other areas to apply these ideas to?" — and the
finding three independent scans arrived at separately.

Value objects now flow *out* of the stat-file layer (`StatObj.stadium()` returns a
`Stadium`, `EventObj.batter()` returns a `Character`), but the modules downstream still
key on raw `str`/`int`. Because `RioValue.__eq__` returns `NotImplemented` against a raw
value and `x in dict` is `False` rather than an error, **every one of those boundaries
fails silently instead of raising**:

```
has_wall_data('Mario Stadium')       -> True     ✓
has_wall_data(Stadium.from_raw(0))   -> False    ✓
has_wall_data("Bowser's Castle")     -> False    ✓   (legacy name, not normalized)
```

So `hit_analysis.game_highlights(stadium=stat_obj.stadium())` — which is what the
docstring example at `hit_analysis.py:11` tells you to write — silently returns
`robbed_home_runs: []` rather than erroring. Same class of failure at
`stadiums.py:160,182,209,373`, `hit_analysis.py:191,209`, and `helpers.py` (fielder
tables keyed by raw int in one file and by name string in another).

**The move:** normalize at the top of every public function that takes a coded value —
`name = Stadium.from_raw(stadium).name`. It is purely additive (it also starts accepting
legacy names and raises `UnknownRioValueError` instead of returning a wrong answer), so
it is non-breaking and can land before or after the cut. This is worth more than any new
value class.

### Where new value classes genuinely fit

- `InputDirection` — `Tables.INPUT_DIRECTION` exists with no class, and
  `stat_file/event_search.py:27` reads the table directly with raw string keys.
- `CharClass` and the other categoricals in `constants/character_data.py:30-57`
  (`CHARACTER_CLASS`, `HORIZONTAL_HIT_TRAJECTORY`, …). These live outside `Tables`, so
  they're absent from the registry and from `list_dicts()`, and can't be resolved with
  `from_raw`. **Note:** changing `CharacterAttributes.char_class` from `str` to a value
  object is breaking, since it's reachable via `Character.attributes`.
- `live_ball.py` collision kinds — but as a plain `IntEnum`, **not** `RioValue`. Those ids
  come from the decomp, not ProjectRio's canonical tables, and CLAUDE.md requires that
  module stay standard-library-only and a faithful port.

### Registry opportunities, in descending payoff

| Where | What's there | Collapses to |
|---|---|---|

## 3. Confirmed bugs — **all six fixed**

> Fixed on `v1.0.0-prep`, each with a regression test that was checked to fail against
> the unfixed code. Suite: 160 passing, up from 137; the 2 `test_canonical_parity`
> failures are pre-existing and unrelated (see section 1).

1. **`StatObj.captain()` raises on every call** ✓ — `stat_obj.py:230` iterates
   `characterGameStats()`, which returns a dict (`stat_obj.py:158`), so `character["Captain"]`
   indexes a string key → `TypeError`.
2. **`EventSearch.runnerOnBaseEvents()` raises on every positive-base call** ✓ —
   `event_search.py:402` calls `self.eventFinal()`, which exists nowhere; the method is
   `final_event()` (`stat_obj.py:711`). Same path has a stray unconditional
   `print('required_bases')` at `event_search.py:401`, and `runner_on_base['None']` at
   `:382` is a `KeyError` against an int-keyed dict.
3. **`calculate_stadium_area()` raises `NameError`** ✓ — `draw_stadium.py:184` uses
   `ConvexHull`, imported only at `:249` inside the `__main__` block.
4. **`lookup()` is case-insensitive in one direction only** ✓ —
   `lookup(Tables.CHAR_NAME, 'mario')` → `0`, but
   `lookup(Tables.SIMPLIFIED_NAME, 'mario')` → `'Invalid ID or Name: mario'`.
   `rio_value.py:461` looks up the *raw* term where `:463` lowercases.
5. **`RioValue` accepts an inconsistent id/name pair** ✓ —
   `Character(0, 'Bowser')` constructs happily and `== Character(0, 'Mario')` is `True`,
   because equality uses `(type, id)` only. A value object shouldn't hold a state
   `from_raw` can never produce.
6. **`outsInInningEvents` validates outs with the half-inning checker**
   (`event_search.py:499`), which accepts only 0/1 — so `outsInInningEvents(2)` raises and
   the negative branch at `:503-506` is unreachable.

That none of 1–3 has ever worked is useful: nothing downstream can depend on them, so
they were free to fix now.

**Two judgement calls made while fixing, worth a look:**

- `StatObj.captain()` now returns `Character | None` rather than a raw char id. The old
  annotation said `-> str` and returned the id, so it was wrong either way; `Character`
  matches `HudObj.captain()`, which already returns one (`tests/test_hud.py:39`).
- `RioValue.__post_init__` validates only when the subclass has a non-empty `_lookup`, so
  the bare `RioValue(0, "Mario")` still constructs. `tests/test_lookup_values.py:35`
  relies on that to assert cross-type inequality. The alternative — making construction
  private and exposing only `from_raw` — is the stronger contract but is breaking, so it
  belongs in the section 4 decision list rather than a bug fix.

### Needs a live check, not a code fix

`rio_web.py:171-177` `_strip_value` does `"".join(v.split())`, which removes *internal*
whitespace ✓ — so a `captain="Baby Mario"` filter goes out as `"BabyMario"`. Whether
that's a bug depends on what the API expects; `userInputToCharacter` is also
space-insensitive, which hints the convention may be deliberate. Worth one query against
a live endpoint before touching it.

## 4. Decisions locked in by the version cut

Grouped by what you'd be committing to.

**Naming.** The 119 camelCase methods, the camel keyword parameters, the public camel
attributes, `result_of_AB`, `first_fielder_maunual_selected`, `userInputToCharacter`,
`glicko2.Player`'s four accessors. There's already a precedent for the cheap answer:
`StatObj.characterName` (`stat_obj.py:208-210`) is a deprecated alias with a test
(`tests/test_stat_parser.py:36`). Adding snake_case names and keeping camel as aliases is
non-breaking and can be done incrementally — but the *decision* has to be made now,
because freezing means owning both spellings forever.

**Error channels.** Whether `lookup()` raises, returns `None`, or keeps the sentinel; and
whether `lookup(auto_print=...)`/`list_dicts()` stay print-based (both exported).
`character_data.py:286` raises `KeyError` where the construct raises
`UnknownRioValueError` — and `is_captain` depends on it. `event.py:21` raises `IndexError`.
`error_checking.py:10` still raises bare `Exception` (the bug CLAUDE.md names), reached
from 19 call sites; `ValueError` subclasses `Exception`, so that one is safe to fix any
time.

**Public coded-value types.** `HitInputs.pitch_type_val` is a packed 0-4 int that merges
`PitchType` and `ChargeType` and matches neither table; `HitInputs.swing` is a third
encoding (swing kind is spelled four different ways across the sim, validator and
analysis). `HitResult.contact_type_name` uses `"Left Sour"` where `Tables.CONTACT_TYPE`
says `"Sour - Left"`. `ContactRecord.batter: str` is actually assigned a `Character`.
`CharacterAttributes.char_class` as `str` vs a value object.

**Data shapes.** `CAPTAIN_TEAMS`, `CaptainTeams`, `Signature` (newly exported in the
uncommitted diff — worth asking whether they should bake first);
`Tables.SIMPLIFIED_NAME` (54 entries, 23 of them identity rows the `.get(x, x)` fallback
already covers); `Tables.HAND` vs `HAND_BOOL` as two tables for one concept;
`STADIUM_WALLS` as five parallel lists; `NOTE_BLOCKS` type strings, which diverge from
the park sheets (`"Note"/"Random"/"Brick"` vs `"note"/"mystery"/"brick"/"used"`, with
four `"used"` blocks omitted).

**Scope.** `helpers.py` is imported by nothing in the repo but documented at
`README.md:53`, so it's public in practice — CLAUDE.md says dissolve it, and that's
cheapest before the cut. `hit_simulation.py:1332` `_inputs_from_event` is underscore-named
but its comment says RioVisualizer calls it. `__init__.py` currently exports whole modules
(`hit_analysis`, `stadiums`) with no stated contract, and omits `CharacterAttributes`,
which users need in order to annotate what `Character.attributes` returns.

## 7. The canonical-parity failures: investigated

**Root cause: the test was reading a dirty checkout, not released ProjectRio.**
`tests/test_canonical_parity.py` resolves its "canonical" header from the *working tree*
of a sibling ProjectRio clone (`../ProjectRio`, or `PYRIO_PROJECTRIO_PATH`). That clone is
on branch `stat-tracker-update` with uncommitted edits to `MSB_StatTracker.h`, and those
edits are the entire source of the two failures.

Against **committed** ProjectRio 2.2.0, pyrio's tables pass **20/20**. So pyrio is
faithful to released Rio; it is the *unreleased* corrections it does not yet have.

### What pyrio is actually behind on

Seven divergences from `origin/2.3.0_release` (which carries `433891805e`, "Stat tracker:
correct at-bat result labels"), triaged:

**A. Adopt now — confirmed wrong today, affects real data**

- **`FINAL_RESULT` ids 5 and 6 are swapped.** Canonical 2.3.0 has 5 = `'Caught
  line-drive'`, 6 = `'Caught'`; pyrio has them the other way round. Confirmed empirically
  against the encoded fixture, where the split is exact:

  | raw id | n | Vert Angle | Ball Max Height |
  |---|---|---|---|
  | 5 | 5 | 58–151 (all ≤ 160) | 1.61–3.81 |
  | 6 | 23 | 165–596 (all > 160) | 4.05–29.89 |

  Which matches the upstream comment (`Hit_VerticalAngle <= 160`) and the physics: id 5 is
  the flat, low-apex trajectory — the line drive. pyrio currently mislabels the **more
  common** of the two, 23 events to 5 in a single game.
- **`CHARGE_TYPE` is missing id 1**, `'Charged Captain Star'` (pyrio has only 0, 2, 3).
  `ChargeType.from_raw(1)` raises today, and that crashes `EventSearch` construction for
  the whole file — see E below.

**B. Adopt with 2.3.0 — mechanical renames**

- id 11 `'Error - Input'` → `'Error'`, in both `FINAL_RESULT` and `SECONDARY_CONTACT_RESULT`.
- `SECONDARY_CONTACT_RESULT`: drop id 16 (`'Foul catch'`), add id 255 (`'None'`). Upstream
  dropped 0x10 because secondary results are only copied up to `DOUBLE_PLAY`, so it was
  unreachable.

**C. Settled by decision: `'Batter safe, throw elsewhere'`**

id 12 has three live spellings: `'Error - Chem'` (2.2.0, and pyrio's), `'Fielders Choice'`
(2.3.0), and `'Batter safe, throw elsewhere'` (proposed in
[ProjectRio/ProjectRio#170](https://github.com/ProjectRio/ProjectRio/pull/170), **open**).
The 2.2.0 value was known-wrong either way — upstream's own commit message notes nothing
in the game sets 0xC from chemistry. **Decision: adopt `'Batter safe, throw elsewhere'`**,
since #170 is going to be implemented. pyrio therefore runs ahead of 2.3.0 on this one
id, which the parity test records explicitly rather than ignoring (see D).

> These strings are what `FinalResult.name` and `SecondaryContactResult.name` *return*, so
> they are part of the public contract. Shipping 1.0.0 with 5/6 swapped makes correcting
> it later a breaking change to returned data.

**D. Make the test reproducible**

The suite's result currently depends on whatever a second repository happens to have
checked out and uncommitted, which is how these two failures came to look like pyrio table
bugs. Read the header from a pinned ref (`git show <tag>:Source/Core/Core/MSB_StatTracker.h`)
rather than the working tree, or at minimum report the resolved commit and whether the
file is dirty in the failure message.

**E. Two bugs found in passing, unrelated to parity**

- **`EventSearch` cannot be built from an *encoded* stat file at all** — it raises
  `KeyError: 2` from `_input_direction_dict` (`event_search.py:27`), which is keyed by

  only ever uses the decoded fixture, so this is untested.
- **A charge type of 1 crashes `EventSearch`** with `UnknownRioValueError`. The

  captain-star pitches will be in real files.

### 5/6 in old decoded files: corrected by version

A footgun in the same family as the `team_num` era flip. **Resolved** — see "The fix"
below.

Ids 5 and 6 were **swapped, not renamed**, so a decoded label cannot be resolved without
knowing which Rio produced it. `'Caught'` means id 5 in a pre-2.3.0 decoded file and id 6
in a 2.3.0 one. A legacy alias cannot help — the same string legitimately maps to both.

Measured on the repo's own fixture pair (one game, `Version: 2.2.0`), reading the encoded
and decoded copies now disagrees on **28 of 211 events**:

```
event 2 : encoded=FinalResult(6, 'Caught')            decoded=FinalResult(5, 'Caught line-drive')
event 13: encoded=FinalResult(5, 'Caught line-drive') decoded=FinalResult(6, 'Caught')
```

The encoded reading is the correct one.

**The fix.** `EventObj.result_of_AB()` now routes the raw value through
`StatObj._correct_legacy_ab_label()` before resolving it. That helper inverts the two
labels when, and only when, the value arrives as a *decoded string* from a file whose
version is before 2.3.0 — the `teamNumVersionCorrection` pattern applied to a label
instead of a team number. Encoded ids are never touched, since the stored numbers did not
change. A file with no readable version counts as legacy, because every such file predates
2.3.0.

Behaviour, all of it pinned by tests in `tests/test_stat_parser.py`:

| file version | decoded `'Caught'` | decoded `'Caught line-drive'` | encoded `5` / `6` |
|---|---|---|---|
| ≤ 2.2.0, or unknown | id 5 | id 6 | 5 / 6 |
| ≥ 2.3.0 | id 6 | id 5 | 5 / 6 |

On the fixture pair the encoded and decoded copies now agree on **all 211 events**, down
from 28 disagreements, and the split matches the measured physics: 23 caught fly balls,
5 line drives. Neutralising the helper puts all 28 back, so the test is load-bearing
rather than vacuous.

**Known gap.** `HudObj.event_result()` (`hud.py:219`) returns the label as a raw string
and `HudObj` is constructed from `hud_json` alone, which carries no `Version`, so it
cannot make the same correction. A HUD label of `'Caught'` from an older Rio is still
ambiguous. Fixing it means giving `HudObj` version context — worth doing when that
accessor is changed to return a `FinalResult`, which section 1 already lists as pending.
